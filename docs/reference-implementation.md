# Grace final proposal workflow

The default connection is now the opt-in desktop ChatGPT browser bridge; see `docs/browser-bridge.md` for its prototype status, pairing requirements and verification limits. The API pipeline below is retained only for the explicitly selected API mode, with separate billing.

The required agent model is pinned centrally to `chat-latest`, which official OpenAI documentation identifies as the latest ChatGPT Instant model. Chat, structured extraction, individual image analysis, visual review and render orchestration all use this ID. Stale `OPENAI_MODEL`, `OPENAI_CHAT_MODEL` and `OPENAI_RENDER_AGENT_MODEL` environment values cannot substitute another language model. Image pixels still come from the explicit `image_generation` tool (`gpt-image-2.5-sunburst`); this tool has its own API usage and is not a free ChatGPT session. The model ID is returned in API responses, including image-generation errors.

The approved `good-work-1(3).pdf` contains 48 pages: six A2, forty-one A3 and one A4. Its archive `workflow_commands_bundle(5).zip` includes the historical R2 finalizer, page index and 67-command manual. The finalizer was inspected, not executed: it contains historical coordinates and modifies files for that earlier building.

The active React pipeline is upload → individual image review → source-plan identification → project data → contact references → concept render → visual comparison → final PDF composition → validation → download. A failure of the conversational text request does not interrupt an otherwise usable proposal pipeline. A missing render cannot be passed off as a complete final proposal.

`lib/referenceProfile.js` pins the approved source hashes, measured page boxes, A2/A3/A4 sizes and required document sections. `src/proposalPdf.js` is the sole PDF implementation. Its main layout is measured from page 1 of the approved PDF. It embeds Cyrillic fonts, every supplied photo, evidence supplements and a final A4 summary. Validation/provenance JSON is embedded inside the PDF, not offered as a substitute download.

For a single source floor, the remaining A2 sheets cover CCTV, networks, power, server/storage and QA. This is an explicit adaptation, not a claim that four source floors exist. The one-floor test produces 22 pages. Source plans retain their image geometry and are embedded without a generative redraw. The original image bytes and SHA-256 are kept separately in the browser artifact store.

Only final PDF attachments are shown in assistant messages. Pending files are cleared synchronously at submit; submitted image previews belong to the sent user message. Upload, drop anywhere in the chat window and clipboard images share the same bounded ZIP/image intake. Existing pending files survive a failed additional upload.

Limits: PNG/JPEG/WebP and ZIP containing those images; up to 100 images, 20 MiB per image, 40 MiB per ZIP, 120 MiB expanded total. PDF/DWG/IFC source ingestion and calibrated vector reconstruction are not implemented. No account synchronization is implied by browser-local chat history.

The reference-section completeness threshold (80%) counts required section types. It does **not** measure visual similarity, factual completeness or geometric accuracy. Automatic visual review is fallible and keeps exact geometry unverified. Exact BIM/IFC, confirmed device positions, installation cable lengths, live product prices and a guarantee of 80% or 100% output fidelity remain outside verified capabilities.

Verification includes table-driven intent tests, real `floor1.zip` expansion, API routing with old Grace context followed by a math question, pending-preview clearing before analysis finishes, button grid placement, PDF page sizes, photo inclusion and Unicode rendering. Actual client command outcomes and timestamps persist in the message, including failures; unused server command templates are not presented as an execution log.

The production ZIP test reviewed all six source images and extracted project data. The image-generation request then returned `You have no credits remaining`. After the Instant policy was published, a new request using the same source plan and all five photographs returned HTTP 429, `credit_balance_exhausted`, with `model: chat-latest`. A fresh end-to-end render/PDF therefore remains blocked by the API account balance. Local PDF export with the prior actual render passed; this does not certify a new production render. A retry can resume from preserved project inputs without requiring the user to upload the archive again; a changed plan cannot reuse an older project's render.
